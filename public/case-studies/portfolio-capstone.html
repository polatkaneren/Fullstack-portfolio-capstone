Case study

Building a documented full-stack portfolio in three weeks

A portfolio site that is also a working full-stack application, planned around measurable goals and documented so that someone else can run, test and extend it.

Summary

In one paragraph

I set out to build a portfolio with two API endpoints, at least 70% test coverage and documentation good enough to reproduce the project. The finished app has four endpoints, 39 automated tests with 100% line coverage, and a pipeline that runs the tests on every push. The most useful lesson came from a failure: every test passed, yet the contact form did not work in a real browser.

The problem

A portfolio usually exists only to show other work. I wanted this one to be evidence in itself: a real full-stack application with a backend, a frontend, tests and deployment documentation. For the course, it also had to show a technical writing process, using structured Markdown, version control and a project board to plan, build and document the work.

Before writing any code, I committed to measurable goals in a metrics file:

  • Two API endpoints: GET /api/projects and POST /api/contact.
  • At least 70% automated test coverage.
  • Three to five meaningful commits per active coding day.
  • Setup, architecture and deployment guides, tracked weekly.

Writing the goals down first changed the work. Each goal became something a reader can check against the repository, rather than a claim they have to trust.

Constraints

  • Three weeks. Anything that did not serve the goals above was out of scope.
  • Readable by a reviewer. A grader should be able to open any file and follow it, without learning a framework or a build tool first.
  • One command to run. After installing, npm start should be the only step.
  • Public input. The contact form accepts text from anyone on the internet, so it needed validation and abuse protection from the start.

Architecture

One Node.js process does two jobs: it serves the website's static files and answers the JSON API under /api. Because the page and the API share an address, the frontend calls relative paths such as /api/projects and works unchanged on a laptop or a hosting service.

The app is built by a function, createApp(), instead of being started directly. A separate file starts the server. That split lets the tests build the whole app in memory and send it requests without opening a network port.

Key decisions

Decision Alternative Why
One server for the API and the website Host the frontend separately One thing to deploy, no hard-coded localhost address, and no cross-site configuration in the default setup.
Plain JavaScript, no framework React with a build step The page is small. Reviewers can read the source exactly as the browser runs it.
App factory, createApp() Start the server inside the app file Tests run in memory, and parts like the message store can be swapped out.
Messages kept in memory A database or an email service Out of scope for three weeks. The store sits behind one add() function, so replacing it later changes one file.
Hidden honeypot field and rate limit A CAPTCHA Blocks simple spam bots without third-party scripts or extra steps for real visitors.

Testing and the bug coverage missed

The tests use Jest with Supertest, which sends real HTTP requests to the app in memory. They cover successful responses, every validation rule, malformed and oversized request bodies, the spam honeypot, the rate limit, security headers, and a failing message store that must not leak its error details. The pipeline fails if coverage drops below 70%.

After the first version, all 36 tests passed with 100% line coverage. Then I opened the site in a real browser, filled in the contact form, and got “Origin not allowed.”

What went wrong

The cross-origin (CORS) check allowed two cases: requests with no Origin header, and origins on an allow-list. The tests sent no Origin header, so they always passed. Browsers, however, attach an Origin header to form submissions even when the page and the API share an address. The server rejected its own website.

The fix

The check now also accepts a request whose Origin matches the server's own host. I added two tests: one that sends a same-origin request the way a browser does, and one that sends a malformed Origin header. The suite grew to 38 tests.

The lesson

Coverage measures which lines ran, not whether the tests describe how the software is really used. Every line of the CORS check ran, but never with the input a browser sends. Testing in a real browser is now a step in my process, not an afterthought.

A dependency audit during the same pass flagged a known vulnerability in the rate-limiting package. Upgrading it left the production dependencies with zero reported vulnerabilities.

Documentation approach

The README is written for someone who has just found the repository and wants to run it. It answers questions in the order a new reader asks them:

  1. What is this?
  2. How do I run it?
  3. How do I configure it?
  4. What does the API accept and return?
  5. Where is everything?

The API reference lists every status code with its meaning and an example body, because a status code alone tells a reader nothing about what to fix. Limits that affect users, such as message length and the rate limit, appear next to the endpoint they belong to rather than in a separate section.

The metrics file is the project's log. It records the goals, the current numbers and a dated entry for each work session, so the numbers in this case study can be traced to where they were measured.

What's next

  • Deploy the site and write the deployment guide from the steps actually taken.
  • Write the setup and architecture guides.
  • Save contact messages permanently, in a database or by email.
  • Add automated browser tests, so a bug like the CORS failure is caught before a person finds it.
